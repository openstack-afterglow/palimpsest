## Context

This is a design delta against origin/dev `b091659`. `spec.md:756–764,864–867,876,1064` and the accepted `base-migration-structure-check` capability govern the product behavior. `ARCHITECTURE.md:39–47` distinguishes the pure implementation from the unwired product path. M4 remains a prerequisite for implementation and qualification; this design makes no stage-completion claim (`spec.md:19`).

## Goals / Non-Goals

Inspect and register exact published `oci-root` combinations for both same-release revisions and supported same-family release changes. Bind every new run to an authorized immutable result and enforce the same acknowledgement policy in all clients. Do not modify the pure algorithm, repair package databases, resolve dependencies or ABI, require a smoke test, publish an `application` disk rebase, or authorize arbitrary M5.5 composition.

## Decisions

### 1. Resolve, verify and list the actual mounted payloads (M51-02)

The Hub exposes a check that writes only bounded, expiring inspection records, and a separate registration operation under published images. A caller supplies three publication UUIDs with their expected **published manifest digests** (not OCI source digests, layer digests, tags or names). The Hub resolves all three through current image-read policy and validates the sealed manifests and membership graphs. Both operations require authenticated authority; registration also requires existing publication rights. Preserve current publish-only key restrictions on reuse. Derive the kept suffix, never accept a caller-supplied layer list. The old base's ordered payload digests must be an exact prefix of the existing image's payload digests, including repeated occurrences; digest/size declarations for identical payloads must agree. Validate all inputs as `oci-root` with matching platform and supported declared OS family. Apply an explicit supported-release policy for the intended runtime; syntactically valid OS strings are not support evidence. A verified replacement within the same family may change the supported release; revision metadata is not used to infer an OS release.

When the existing combination is a managed migration, the old base must match the exact publication UUID and manifest digest of its recorded replacement base. A matching prefix or a republished copy does not substitute for that binding. Refuse if the old and replacement bases have the same published manifest digest or identical ordered payload digests, including repeats. Different names, UUIDs or labels do not replace runtime bytes.

Inspect the exact authorized, storage-bound SquashFS bytes. Open immutable/pinned handles and verify digest and size before parsing; bind the same verified inputs to registration. A userspace read-only SquashFS adapter in an isolated, bounded worker walks inode/directory and xattr records and streams file data for hashes. Do not boot, mount tenant images in the API host kernel, extract a host filesystem tree, follow symlinks, open special devices, or accept host paths, arbitrary URLs or reader commands from the request. Set finite CPU, time, expanded-byte, entry/path and memory budgets. Validate reports and adapter outputs at the service boundary. CLI and dashboard use this Hub operation rather than assuming equivalent permissions, host tools, or parser capabilities locally. OCI tar, compressed descriptors, conversion receipts, `unsquashfs` text output, and CAS magic-byte checks do not prove the stored tree or its completeness.

Before opening or hashing payloads on a cache miss, reserve a worker slot under configured finite limits for the exact subject, project, and Hub deployment (shared across API replicas). Apply per-subject and per-project request rate limits, bound report storage globally and per scope by count and bytes, and reject excess requests with a retryable capacity error; do not enqueue an unbounded backlog. Release worker reservations on completion, cancellation or timeout after the worker has stopped. Capacity rejection before a report can be sealed is unavailable service, not a result eligible for acknowledgement. Coalesce checks and reuse unexpired sealed records only for the exact ordered image UUID/digest pins, inspection target, policy and reader version/budget, and authenticated subject/project scope; reauthorize access on every hit. Quota on inspection does not replace publication or runtime quota.

The adapter projects an ordered list per payload occurrence and separate root evidence. Enumerate stored relative paths exactly as strict UTF-8 with case and code points preserved; refuse malformed or contradictory entries. Include stored synthesized/inherited parents and their attributes. Expand hard links by path; hash full regular-file bytes; record kind, numeric uid/gid, permission and special mode bits, regular-file size, symlink targets and device numbers. Translate the payload's recognized overlay whiteout/opaque representations, including marker names, native whiteout devices and control xattrs, using the actual runtime interpretation. Refuse malformed or unrepresentable controls rather than treating them as normal files. Hash the complete raw xattr set using the accepted padded-base64 canonical JSON, including the empty-set digest, across namespaces (capabilities, ACLs, SELinux); omit only translated overlay controls. Ignore timestamps. Never emit the root as an `Entry`: prove root opacity absent on every input; compute the new base's effective runtime root metadata from the ordered lowers; require every kept root's mode, uid, gid and canonical xattrs identity to match. Unknown root equality or opacity is a refusal, not an overrideable coverage gap.

Separate **topology coverage** (all paths, kinds and hiding controls, with required entry fields) from **identity coverage** (regular-file content and xattrs). `base_migration.check` interprets missing map keys as known absence and a missing kept directory can manufacture an ancestor finding. Use these inputs without modifying the pure comparison:

- If every payload in both bases has complete topology, flatten each base in its published order. If every visible base entry has a canonical xattrs identity, compare all complete-topology kept occurrences; pass an empty listing at the original ID and index for any kept occurrence with partial topology. Keep absent file content and kept xattrs identities absent. The pure comparator detects unavailable file content and one-sided xattrs; a known base xattrs identity prevents two null identities from being treated as equality evidence.
- If any base payload has partial or unavailable topology, or a visible base entry lacks an xattrs identity, suppress the entire base comparison. Call `check` with two empty maps and an empty listing for every kept occurrence at its original ID and index, with `complete=False`. Missing base paths and two-sided unknown xattrs can no longer manufacture findings. Validate all observed records before this decision; a proven malformed or contradictory listing still refuses.
- Set `complete=True` only when every base and kept occurrence also has full identity coverage, including entries flattened away. `layers[].entries` counts only entries supplied to `check`. A bounded service coverage member identifies excluded occurrences and why (`base-topology-unavailable`, `kept-topology-unavailable` or `identity-unavailable`, with any applicable inspection reason). Counts, retained findings and truncation come unchanged from `check`. Zero findings when comparisons were excluded means no comparison evidence, not zero conflicts.

Treat root admission as an independent metadata pass over the verified bytes, before non-root enumeration. This makes an unavailable non-root inspection representable even if no non-root entries can be inspected:

| Failure class | Result |
| --- | --- |
| Root admission and all other hard checks pass; one or more non-root listings are partial or wholly unavailable | Return a sealed `incomplete` report with `inputs_complete: false` and a bounded coverage reason. Examples: a non-root inspection worker cannot start or finish after root admission; the inspector cannot enumerate non-root records that the supported runtime can read; file-content or xattr identities are unavailable. Preserve ordered layer identities even for unenumerated layers. Report only findings supported by the observed coverage; never interpret an unenumerated path as known absent. Registration can proceed only with dedicated acknowledgement and an exact report pin. |
| Root opacity is present or cannot be ruled out, or required kept-root equality fails or cannot be proved | Refuse regardless of acknowledgement. A reader or format that cannot read even the required root metadata lands here, even if the stored byte hashes match. |
| An input is unauthorized, missing, digest/size-mismatched, structurally invalid, unsupported, or otherwise fails hard admission | Refuse regardless of acknowledgement; a proven contradiction is not a coverage gap. |
| The service cannot emit an authoritative report at all (for example the check service is down) | No admission decision can be bound to the request. Retry the check when available; a client-supplied verdict or acknowledgement cannot replace a report. |

This is the proposed reading of `openspec/specs/base-migration-structure-check/spec.md`: the verdict rule for an unenumerable image at line 89 applies after required root admission at line 33. An unavailable non-root listing does not override root admission. Confirm this product boundary before implementation.

Enrich the pure report with all three manifest digests, their declared OS values, `os_release_changed`, bounded coverage evidence, and the effective risk verdict with its contributing migration bindings. Leave the pure `verdict`, `requires_risk_acknowledgement`, findings and counts unchanged; the pure fields describe this comparison only. Hash the full enriched report with `base_migration.report_digest`; keep its identity outside the report. Do not add times, actor names or request IDs to report identity. Before returning the report, seal it server-side with its digest, exact ordered input UUID/digest pins, inspection target, authenticated scope, policy/reader version and expiry. This record is review evidence, not a publication or a grant. It creates no image, durable blob references or run. A later recheck must not overwrite a still-valid record with a different report.

### 2. Register a new immutable publication (M51-02, M51-05)

Registration requires an explicit output name, visibility, request UUID, check reference and expected report digest. Rebind to that exact unexpired, scope-bound server-sealed check record; verify its digest and policy version. Do not rerun inspection at registration: wall-clock budgets or worker availability can change the report and make an acknowledged incomplete result impossible to register. If the sealed record is stale, absent, mismatched or invalid, require a new check and, where needed, new acknowledgement. At commit, revalidate the exact pins, current subject/read/reuse authority and verified storage, and take the existing lexical blob locks before the image SQL mutex. Keep inspection and expensive read-only work out of that mutex; use verified pinned handles or reverify content if the storage identity changed. Reuse normal publication quota, visibility and scoped storage promotion/reference paths. Matching digest, staging ownership or another visible publication must not erase the exact inputs' reuse constraints. Preserve inherited ceilings for contributed occurrences and recheck provenance and diagnostics against source audience policy, even for bytes already in CAS.

Normalize a new manifest with the replacement base's OS version and platform. Use top-level `source` with `kind: local` and a server-owned `source.metadata.migration` binding containing the report digest, comparison verdict and effective risk verdict. `normalize_manifest` permits source metadata; the manifest digest commits to the binding while `public_manifest` omits it. Do not copy OCI registry/reference, manifest, config, root or DiffID claims. Omit per-layer `source`; old ordinal-bound receipts would falsely describe the new chain. Record verified origin slots separately in service-owned provenance. The ordered payload sequence is exactly the replacement base plus the kept suffix, by digest, size and occurrence. Recompute parent-bound logical IDs; deduplicate physical bytes, not positions or authority. Bind the committed record to the new publication UUID and manifest digest, with exact UUID/digest pins for the origin and both bases, the full report and contributing migration bindings, both verdicts, and authenticated subject and UTC time when acknowledgement was required. Retain the complete report and restricted audit evidence independently of check-cache expiry. Never reuse a donor's full OCI source closure or invent a build job.

Classify publication origin using server-owned data, never the presence or absence of `source.metadata.migration` alone. During a drained-writer cutover, classify the exact pre-feature rows as legacy ordinary without modifying their manifest bytes. A legacy ordinary row with no server migration record keeps existing behavior: any caller-written key is inert. After cutover, reserve the key on ordinary publication/import and record the producer's origin class at commit. A managed migration must have its server origin class, matching marker and matching committed record; a missing class or a contradiction among them is a hard error, not legacy fallback. Runtime authority comes from the server classification and validated binding, not from user metadata.

Seal the new publication, memberships, migration record and durable blob references in the same write transaction. A refusal exposes no new publication and never mutates the original. An identical authenticated request UUID and request return the committed result without another write, even after the preview expires; verify current result/read authority on replay. A different actor, check reference, inputs, expected report, acknowledgement intent or output cannot take over that UUID. Do not retag the original, alter its graph, consume its references or redirect its consumers. Its original run policy remains unchanged; if it was itself a non-clean migration, it still requires its own acknowledgement.

### 3. Enforce the risk gate at each real consumer (M51-03, M51-04)

| Authoritative state | Registration or fresh run |
| --- | --- |
| Effective risk verdict `clean`, with complete evidence and a valid sealed identity | Allowed without acknowledgement, subject to every normal check. |
| Effective risk verdict `conflict` or `incomplete`, whether found by this comparison or inherited | Block without dedicated acknowledgement; allow only compatibility risk after all other checks pass. |
| Hard refusal, missing/malformed/tampered mandatory provenance, or no authoritative report | Block even with acknowledgement. A genuinely pre-existing non-migration image keeps its current policy. |

The gate covers server-recorded migration lineage, not every independently submitted stack that happens to contain the same bytes. For a migration, compute `effective_risk_verdict` as the strictest of its pure comparison verdict and the validated effective verdicts of the existing combination and replacement base (`incomplete` > `conflict` > `clean`). An ordinary publication contributes no migration verdict. The old base is inspection-only; it is not an additional runtime lineage input. Use the existing combination's gate even when the kept suffix is empty: the new comparison cannot clear prior risk. Preserve the prior gate instead of refusing every later migration, so users can move to a different base without losing earlier risk evidence. Validate the immediate lineage inputs' immutable seals before computing the result and again at registration. The enriched report records each contributing migration's role, exact publication manifest digest, sealed report digest and effective verdict. Each digest commits transitively to that report's ordered ancestor links. Keep those reports in durable provenance; do not copy an unbounded ancestor list into each new report. Consumers verify the persisted binding rather than recomputing from filesystem data or treating a missing lineage record as ordinary.

Refuse `/published-images/extensions` and any non-migration server derivation that names an effectively non-clean runtime ancestor, even with acknowledgement. Check at the final publication boundary as well as the endpoint. An extension did not run the migration check for its changed stack; refusal avoids implying the earlier report covers those extra layers. Preserve existing ordinary publication by digest with its current payload authority, scope and quota checks. Such publication is neither a managed migration result nor a `clean` attestation; matching digests alone neither apply nor remove an existing migration gate. General composition policy belongs to M5.5.

CLI uses `--yes-i-understand-the-risk` for migration registration and managed run, create, start or resume. Hub uses the strict JSON boolean `acknowledge_compatibility_risk: true`; omission or `false` does not acknowledge and non-booleans are invalid. The dashboard displays the selected immutable image, comparison report and effective risk, and sends `true` only after a dedicated, initially unselected confirmation. Clear confirmation when the image, digest, report, user action or authenticated scope changes. Keep the control separate from generic `--force`, `--yes`, confirmation/recreate controls, `--force-architecture`, registration history, and provider/operator approval. The Hub checks current authentication, authorization, ownership, visibility, payload/manifests integrity, resource quotas/limits, platform, supported OS and existing operator requirements regardless of the boolean. Local clients are not the authority for Hub execution.

Bind each supported consumer to a validated image UUID, manifest digest and sealed effective risk verdict before new allocation, launch or other runtime side effects. Both direct Hub native create and the owner-approved dashboard/API launch path must pass the gate; `image_job_id`, `source_instance_id`, boot-image IDs and unscoped layer digests are not substitutes. An alternate selector that resolves to a migrated publication must preserve the same binding and decision. Exact authenticated replay and first-launch steps such as `/advance` for an already admitted create may reuse that launch's decision. A separate create, clone/recreate, run or explicit power-on requires fresh intent. Carry the binding across restarts of the management process; never default missing or unverified migration status to clean. Preserve prior ordinary-image request identities when acknowledgement is absent.

Treat a dev `/instances/{id}/resume` that starts a stopped server or unshelves one as a fresh run, even though it retains the same VM and writable data. Revalidate under the existing instance mutation fence against the retained publication binding before provider start/unshelve or a trust/state change; no create acknowledgement carries over. For non-clean instances, expose the same fresh CLI flag, SDK strict optional body member, and dedicated dashboard Resume confirmation. Preserve omission for clean and ordinary images. A true read-only observation or exact replay that does not trigger a new run needs no second confirmation; do not retry an uncertain provider mutation automatically. Apply the same rule to supported local `start` from retained state.

For non-clean results, resolve an omitted restart policy to `no`, reject explicit `unless-stopped` before allocation even with acknowledgement, and never generate a guest restart capability or restart directive. This includes the Hub service/readiness default and the managed native VZ production default where applicable. Restarting a crashed or exited command would otherwise be a fresh execution with no opportunity for fresh intent. Clean and ordinary images keep their current restart rules.

For a managed CLI local run from a Hub publication, use a publication-aware selector and verified pull/catalog/launch binding. Launch must consume the exact registered lowers, or verify that prepared lowers match every ordered registered digest and size before launch. Do not offer the current unbound OCI layout run hint for a migrated combination. Generic local OCI path/registry flows remain independently sourced; neither a renamed managed record, another managed selector, nor relabeling a server-derived result may strip the gate. The scope question below covers which managed runtime lane the product commits to, not whether that lane enforces risk.

### 4. Explain the result and keep the original reusable (M51-05)

CLI text and structured output, Hub responses and dashboard show the exact report statement, comparison verdict, effective risk verdict, inherited risk when present, coverage and truncation, the separate `package_state_conflict` count for this comparison, and the declared old/new release. A clean comparison must not make a non-clean inherited gate look clean. Package-state findings are structural overlaps (for example `var/lib/dpkg/status` or an RPM database), not a solver diagnosis. Do not imply `0` from incomplete enumeration means no package-state conflicts. Always say `clean` is not a guarantee: the check does not prove ABI, package dependency or runtime compatibility; verification remains the user's responsibility. Show original and result under separate identifiers/digests; offer the normal authorized image detail, pull and launch entry points for the original with its own prerequisites and risk policy. Registration is not successful execution or recovery. Render filesystem paths as untrusted text; do not put raw report paths in broad operator logs.

The pure report's `requires_risk_acknowledgement` describes only the current comparison. Neither this flag nor a comparison `clean` is a launch decision. `compatibility_stages._from_structure_check` can map `clean` with complete inputs to `PASSED`; label that result as the filesystem comparison stage only, not risk clearance. Surface the effective gate separately when a verified binding is available. With no verified binding, the status adapter must not infer clearance from a stage result.

## Owner decisions required before implementation

Only decisions that change product behavior or an authority boundary remain here. Transport route spelling, table names, parser library and copy/dedup details are engineering choices.

1. **Supported runtime and OS release matrix (product/operator).** Which same-family release pairs and runtime lanes are supported for a managed migrated run? The ordinary dashboard `/instances` lane currently requires contextual image-job provenance; native `/native-instances` already takes an immutable publication but requires a separate operator grant. Choose whether to authorize direct publication binding in the ordinary dashboard lane or expose an existing operator-authorized lane. Confirm the supported Linux/KVM and Apple Silicon/VZ local launch matrix; extending a boot profile is a separate decision. No unsupported lane may become runnable just because inspection is clean.
2. **Runtime configuration inheritance (product/security).** Should the migrated combination retain the original combination's exact runtime config (recommended: entrypoint, command, environment, working directory and user), or should the new base's defaults replace it? Choose one explicit policy, including what the user sees before accepting. No implicit merge or copying private runtime metadata into public projections. This changes startup behavior even when all filesystem paths compare clean.
3. **Diagnostic/provenance audience (security).** The result's audience can include readers who could not read an inspection-only old base; the full report can reveal its paths and attributes. Confirm either restricting publication to an audience authorized for all three inputs (recommended; preserve existing reuse ceilings regardless), or permitting a wider result with a separately authorized full report and strictly non-sensitive summary. Keep any required published digests, verdict, counts and warning auditable; if their disclosure would violate policy, refuse the wider result. Decide who may see acknowledged-by identity/time beyond authorized audit principals. No implicit public report or widening by acknowledgement.
4. **Boundary for unavailable inspection (product/security).** Confirm that acknowledgement covers a wholly unavailable non-root listing after root admission, but never missing root evidence or an unsealed report (recommended). If the product is to allow migration when no root opacity/equality evidence can be obtained, that requires an explicit change to the accepted root-admission contract, not an interpretation of `incomplete`. Authorization, integrity, quota and supported OS/platform remain non-overrideable in either case.
5. **Server-derived publication policy (product/security).** Confirm the proposed boundary: refuse non-clean extensions, retain earlier risk on re-migration from the exact recorded base, and refuse same-manifest or same-payload replacements. An alternative may admit extensions only with an enforceable inherited gate; it must not strip prior risk. Ordinary independently authorized digest reuse stays outside the managed migration contract. This means a publisher can republish a non-clean result's exact payloads as an ordinary image, then migrate that copy to an eligible base and get a managed `clean` result if the new comparison and the replacement base's gate are clean. The ordinary copy already follows ordinary execution policy. Confirm this lineage-only boundary rather than treating it as a byte-wide denylist.
6. **Workload restart policy (product/operator).** Confirm that a fresh start/resume needs fresh intent and a non-clean workload defaults to no automatic restart. Reject explicit `unless-stopped` for non-clean workloads rather than silently overriding it. No alternative may reuse registration or create intent as blanket permission for later runs.

## Qualification and rollback

After owner decisions and the M4 dependency are cleared, qualify current converters against known stored fixtures, then exercise preview/registration/launch/replay using exact immutable pins and verify original reuse. Source checks are not boot evidence; obtain separate scoped live approval and independent GATE evidence per `spec.md`. A future schema addition must use the existing reviewed offline migration and rollback process. If an older consumer cannot enforce the new gate, do not expose migrated records to that consumer during mixed-version rollout or rollback; drain/disable affected launch paths before downgrading. Do not change migration verdicts or remove originals to make a downgrade work.

For rollback to writers that predate origin classification, drain writers first and retain a trusted inventory of existing publication UUIDs, manifest digests, origin classes and migration-record identities. Keep existing managed rows and their provenance outside any path that cannot enforce the gate. Permit ordinary publication while rolled back only if this isolation and capture of the exact rollback interval can be established; otherwise disable publication. On roll-forward, drain writers again and reconcile against the inventory before opening ingress. Enroll a new row as legacy ordinary only if it is proved to have been committed by the old ordinary writer in that interval, is absent from the pre-rollback inventory, and has no server migration record or origin class. Keep its manifest unchanged and ignore any caller-written marker. Never reclassify an inventoried row because its provenance is missing; unexpected, changed or unproven rows remain blocked until reconciled. Do not infer rollback origin from a timestamp, absence of records, or client metadata alone.

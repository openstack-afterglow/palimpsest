## Context

Baseline: origin/dev `b091659`; roadmap `spec.md:766–773,994`. M4 and M5.1 are prerequisites. `spec.md:19` permits unrelated design while they are blocked, not downstream implementation or completion claims. The table below uses the upstream [Dev Container metadata reference][ref], [normative specification][upstream] and [base schema][schema]. The Palimpsest mappings are deliberately narrower, not a claim of Dev Containers or Docker compatibility.

## Goals / Non-Goals

Proposed first lane: one allow-listed, full-commit Git Dockerfile build on Hub `linux/amd64` → private publication → fresh CPU development VM using Hub `/instances`. CLI and SDK use the same API as the Hub dashboard; an external dashboard must use that contract too. The application runtime in this lane is the verified job stack mounted as a guest overlay and entered through a chroot. It is not the VM's PID 1 root. Do not substitute it for M4 actual-root evidence or conflate it with `/native-instances`, local VZ/KVM, or ordinary `palimpsest build`. No direct local-checkout import, image-based workspace recipe, Compose, automatic host workspace sync, Docker CLI/API, or browser IDE. No implicit provider, architecture, production or GPU support.

## Decisions

### 1. Explicit discovery and bounded input (M52-01)

No discovery on ordinary requests. An explicit devcontainer source variant supplies the existing HTTPS Git URL and exact 40-hex commit, optionally selecting a config path. The Hub reads one bounded snapshot from that pinned checkout, not the client's local disk or bytes pasted in a dashboard. Without an explicit path, try `.devcontainer/devcontainer.json`, then `.devcontainer.json`, then the sole `.devcontainer/<one-level-name>/devcontainer.json`. This follows upstream precedence; the locally defined tie rule rejects multiple third-tier choices and requires selection. An explicit choice must name one of those layouts and overrides discovery, never merges files. No ancestor search, fallback on malformed/unsafe candidates, aliases or config inference from an image. Missing, unmatched case, invalid explicit selection and ambiguous discovery are distinct refusals. Use case-exact UTF-8 names, no Unicode normalization.

Config, context, Dockerfile and selected ignore files must stay inside the pinned checkout. Resolve `build.dockerfile` and `build.context` (and their legacy counterparts) independently from the config's directory, not the context root. A leading sequence of `..` components may ascend only within the checkout (`..` from `.devcontainer` can select the root); reject interior `..`. Omission of context means `.` at the config directory. `${localWorkspaceFolder}` upstream means the opened host source folder; here it is accepted only as a complete leading token in those build paths, optionally followed by a relative suffix with no `..`, and denotes the pinned checkout root, never a host path or mount. Reject all other `${…}` substitutions, including `localEnv`, `containerEnv`, workspace names/basenames and `devcontainerId`; no shell expansion or defaults. Reject absolute paths, Windows drive/UNC syntax, control/NUL characters, backslashes, empty components and reserved `.git` components. Canonical build paths are checkout-relative. Check every selected path component with no-follow, checkout-relative opens inside the owned snapshot; reject links (including in-root links), special files and nonregular config/Dockerfile/ignore leaves. Context must be a real directory. Dockerfile may be outside the context, still inside the checkout; stage its bytes independently. Other context entries obey the regular Git packer/extractor and link rules; reject context links that resolve outside the context, into excluded input or into protected checkout metadata. Check deterministic normalized paths against the same files used for packing/reading, not a mutable checkout reopened after validation.

Read at most 64 KiB of strict UTF-8 JSONC with one object root. Accept `//` and `/* … */` comments only outside strings; reject BOM, trailing commas (upstream schema sets `allowTrailingCommas: false`), duplicate keys after JSON decoding at any depth, malformed Unicode/surrogates, NUL/control characters in keys, non-JSON constants, and invalid shapes. Enforce depth ≤16 (root depth 1), at most 1,024 values plus object keys counted together, 128 members per object/array, 128 UTF-8 bytes per key, and 4,096 per decoded string. Apply bounds while scanning/decoding, not after unbounded materialization. Existing request, fetch, checkout, context, worker and user-data limits still apply; a stricter limit wins. Never dereference `$schema` or a URL from config.

### 2. Closed field policy and precedence (M52-01/02)

`Supported` means only the typed values below. The mode, authorization, bootstrap, requested resource IDs/limits and security policy always come from Palimpsest. A user must explicitly choose the import and later explicitly create a new VM. Invalid/unsupported config remains an error even if a caller override would mask it. Default native build path flags are treated as omitted for import; any explicit competing Dockerfile, context, target, build-argument or context-archive choice is a conflict, not a fallback. Publication name, request UUID and OS declarations are required native parameters; publication is private only.

After JSON decoding, any occurrence of the exact two-character sequence `${` in an otherwise accepted field key or string value is `devcontainer_unsupported`, even if incomplete or escaped in the JSON source. The only exception is one complete `${localWorkspaceFolder}` token at the start of one of the four build path fields, followed by end of string or `/` and a valid relative suffix. A second `${` anywhere in that value fails; `$` without `{` remains literal. This applies to otherwise harmless annotations too.

The existing Hub launch inputs keep their own semantics: the caller controls `command` and `readiness_argv` as well as native resource choices and explicit dev lifecycle. `InstanceRequest` (`extra="forbid"`) has no cwd, user, env or port-mapping overrides, and this change adds none. Policy always wins; only the supported profile fields below overlay the verified OCI defaults.

| Property | Upstream meaning | Palimpsest policy |
| --- | --- | --- |

| `containerEnv`, `remoteEnv` | Container-wide env; tool/terminal-specific env. | **Supported:** literal non-secret variables scoped to workload/readiness and managed sessions only. | `features`, `overrideFeatureInstallOrder` | Install Feature code/options and override dependency install ordering. | **Rejected:** no Feature resolver, OCI/local Feature download, script, dependency graph or metadata merge. | `customizations` | Tool-specific metadata, often editor settings/extensions. | **Ignored with notice only for `{}`**, which cannot change an outcome. **Rejected** when nonempty or malformed. No tool extension, task or browser IDE installation. |

| `initializeCommand` through `postAttachCommand`, `waitFor` | Stage-specific commands and readiness wait selector. | **Rejected**, detailed below. No empty-valued, `--force`, native override or other bypass. |
| Any unlisted property or child in a closed object | Extensions, unknown fields or misspellings. | **Rejected:** no pass-through or guessed alias. Typed maps (`args` and env) validate their own keys and values. No inheritance from `devcontainer.metadata`; refuse the label by presence in the selected verified image config before publication, regardless of value. No metadata-derived execution. |

Environment keys use the native `[A-Za-z_][A-Za-z0-9_]*` grammar (≤128 bytes). Reject these keys in config: `PALIMPSEST_*`, `LD_*`, `DYLD_*`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `SSH_*`, `ENV`, `BASH_ENV`, `PYTHONPATH`, `PYTHONHOME` and `PATH`. The managed projection does not inherit these keys from OCI; runtime-owned identity and path defaults stay in force. Report that exclusion without values. Other duplicate OCI keys or invalid runtime entries fail. Config env strings are literal UTF-8 with no control characters (except TAB and LF); null is permitted only for `remoteEnv`. Use a trusted clean environment before dropping credentials. Never feed OCI/env data into trusted launchers or shell interpolation. Cap each user-supplied env map at 64 entries and each value at 4 KiB. Cap the UTF-8 bytes of effective workload and session `key=value` entries together at 16 KiB or the smaller bootstrap envelope. Audit key names/source tiers only when safe; never log raw config, unknown keys, values, argv, host paths, credentials or command output as diagnostics. A caller attests supported inputs contain no secrets; arbitrary secrets disguised as literals cannot reliably be detected. Publish neither the profile nor its runtime env as image metadata.

This proposal does not deliver the selectable-volume clause of M52-02. Retaining an instance-private upper is not selectable-volume support. See owner decision 5; M52-02 and its GATE remain open.

### 3. Lifecycle: no execution from config (M52-01)

Upstream [lifecycle][lifecycle] distinguishes a host hook from commands inside the primary container, strings via `/bin/sh`, arrays via direct argv, and objects via parallel commands. No accepted config runs any of these forms. The last column identifies the earliest corresponding event for a *separate* future guest-only proposal; it reserves no hook now.

| Property | Upstream event | VM boundary if separately proposed |
| --- | --- | --- |
| `initializeCommand` | Source-host initialization before image creation, potentially repeated. | No equivalent. Never run on notebook, API host, build worker, VM carrier OS or during config read. |
| `onCreateCommand` | First setup when main container first starts; prebuild can use it. | Once per new VM, in mounted workload overlay after identity/workspace validation, not during build or restore. |
| `updateContentCommand` | After `onCreateCommand`, when source arrives/changes during creation, possibly repeated in prebuilds. | Only after a verified staged workspace is present; no refresh/prebuild event today. Never trigger from host edits. |
| `postCreateCommand` | After content update, on first assignment to a user; may finish in background upstream. | Only after new-VM setup for the exact owner, before developer readiness in any future synchronous policy. Never use user credentials just because upstream permits user-scoped assets. |
| `postStartCommand` | After each successful start. | After the workload overlay is ready on first boot or actual start/resume, not status reads, polling or request replay. |
| `postAttachCommand` | On each successful tool attach. | Only an authenticated managed workspace attach, not provider `ACTIVE`, console-log viewing, raw SSH observation or background polling. |
| `waitFor` | Setup stage that blocks tool connect; defaults to `updateContentCommand`. | No hook/readiness equivalent in v1; Palimpsest readiness and attach gates apply. |

If the owner later chooses any guest hooks, require an independently reviewed, explicit approval bound to the config digest, user and instance, no host hooks or host/project/bootstrap credentials, an unprivileged identity in the workload root/cwd, bounded execution and observable outcomes. Define durable per-event replay/failure, attach ordering and stop/resume behavior before accepting any hook. Features need a separate supply-chain policy for verified publisher/digest and dependency pins, bounded allow-listed fetch and isolated installation, and a review of all requested metadata effects. Neither a trusted Git host nor a generic confirmation authorizes hooks or Features.

### 4. Pure conversion, custody and user surfaces (M52-02)

Split effectful snapshot staging from a pure `convert(config_bytes, selected_path, policy_version, capabilities)` boundary returning a typed, versioned plan or bounded diagnostics. The source adapter does discovery, no-follow reads and packing; the converter performs only lexical validation, classification and mapping. Neither it nor error reporting reads filesystem, cwd, clock, environment, registry, provider or user secrets. Return separate build inputs (Dockerfile, context, args, target), private dev inputs (label, workspace, identity, env, port intents) and notices; no generated shell, Dockerfile, `palimpsest.yml` or VM command. A second pure projection merges accepted profile inputs with verified OCI defaults under runtime policy and resolves the existing native `command`/`readiness_argv` selection. Actual guest identity/path checks follow. No partial executable plan on refusal. Encode versioned plans as compact UTF-8 JSON with object keys in code-point order, no Unicode normalization, no optional whitespace, no platform-dependent paths, and canonical omitted defaults. Preserve semantic array order and sort the port set. Same inputs yield the same plan bytes, digest and diagnostic order, not necessarily bit-identical builds.

Return a stable classification (`devcontainer_missing`, `devcontainer_ambiguous`, `devcontainer_invalid`, `devcontainer_limit`, `devcontainer_unsupported`, `devcontainer_conflict`, `devcontainer_policy_denied`, or ignored-annotation notice), repository-relative selected path when safe, and JSON Pointer for known fields plus 1-based line/column when available. For unknown/untrusted names use the nearest known parent plus position, not a raw string. Sort semantic diagnostics by pointer/code/position, retain at most 32 and signal truncation. CLI exits nonzero and renders the Hub diagnostic; API returns 422 for semantic refusals, 413 for a byte-size cap and 409 for replay/pin conflict; existing auth/scope/rate-limit statuses are unchanged. Dashboard renders the same errors/notices as text, and SDK exposes them without translating failures into success. Never fall back to an ordinary build. After bounded Git staging, invalid source/config creates no queued job, registered context, publication, or provider allocation; sweep only owned transient scratch.

Keep original-human writer authorization, pinned fetch/checkout and bounded staging; preserve current image-policy checks before fetch and at solve, worker lease/custody, storage and publication quotas. The import variant uses the existing Dockerfile executor, with typed args/target, not a Dev Containers CLI or second builder. Its recursive staging uses the existing bounded Git ignore grammar (rejects `!` and `**`) for the selected Dockerfile-specific `.dockerignore` if present, otherwise the context-root `.dockerignore`, plus context-root `.plmignore` as additional exclusions. Check ignore inputs as regular files without symlinks and enforce a combined byte/rule/work budget. The Hub's ordinary Git path currently reads just context-root `.dockerignore`; implement this import policy explicitly, not by assuming parity with local BuildKit. Exclude `.git`, the selected config and other recognized config candidates from the context as mandatory exclusions; config can still be read before packing even when a rule excludes it. Hash the effective ignore rules and exact context tar; never widen `COPY` through an ignored path. Refuse unsupported ignore syntax instead of falling back. Guest-root `/.plmignore` for commit/capture is a separate rule set with mandatory exclusions; do not copy host ignore rules into it, reinterpret data retention as capture, or add Hub capture in this change.

At admission seal server-owned provenance: admitted source locator and commit, selected config path and raw-byte SHA-256, converter/schema version and policy/profile digest, normalized Dockerfile/context paths, Dockerfile/context/effective-ignore digests and exact source policy binding. Store only necessary normalized runtime inputs in creator-scoped state; do not retain raw config or transfer dev settings to the worker. Worker receives the admitted build descriptor and verifies the resulting config lacks `devcontainer.metadata`. Bind the profile and job to the resulting private publication UUID/digest and exact ordered layers atomically with existing completion; avoid changing their runtime config, hashes or public projections to encode developer settings. Exact caller/UUID/descriptor replay reuses the same receipt (no re-fetch or policy reinterpretation); changed source, revision, selector or native descriptor conflicts. At launch revalidate owner, artifact and supported/enabled policy under current authorization, not merely the original build receipt. Caller-written metadata or matching layer bytes cannot create a managed profile. Reject alternate selectors of that same managed job/publication that would bypass the profile, including service or direct-native launch, and reject managed clone by `source_instance_id`; use the exact job for a fresh dev VM. Independently sourced ordinary artifacts with no managed binding retain existing behavior; never infer managed status from equal layer bytes.

Classify managed origin at commit using the server-owned receipt, not a caller-authored marker or a client launch flag. Any managed job/publication missing its matching receipt, or with contradictory digests, is an integrity refusal. Put only the build fields needed to execute in the worker claim; verify the no-label result against the exact job output before admission to publication. Do not forward caller-controlled request metadata as dev-profile provenance.

Upstream [image metadata][labels] lets prebuilt images carry settings in `devcontainer.metadata` and merges them with the file. This lane does not merge or ignore it. If that key occurs in `config.Labels` of the exact built result (including an empty value, inherited from a base or set by the Dockerfile), the worker rejects it after solve and verified OCI config read, before publication intent or output staging. The original job admission remains HTTP 202; settle the leased job as terminal `status: "error"`, `error_code: "devcontainer_image_metadata"` through the existing failure path and cleanup rules. No publication or VM launch. Authenticated image-job list/detail returns the terminal receipt (HTTP 200 for a successful read). SDK preserves the structured status/code. CLI job status and dashboards show the stable code and a safe explanation without the label value; a build-wait CLI command exits nonzero, and the dashboard never enables launch. Author docs must warn that common prebuilt Dev Container bases can pass JSON validation, consume a build and then fail if the final image retains this label; use a compatible unlabeled base instead. No claim is made about labels in any particular uninspected image.

`devcontainer_image_metadata` is a job outcome, not an admission HTTP error. Accept it only from the authenticated, currently leased worker on a managed import. Preserve the ordinary cleanup-failure priority and never turn it into a retry or a successful job.

New VM admission binds the exact job/publication/profile digests and the validated effective settings in its immutable request/retained state before provider effects. Require explicit `lifecycle=dev` (not current `service` default), existing owner-managed SSH key/network/security groups, qualified CPU boot image and `restart=no`. In the local CLI vocabulary `prod` and Hub `service` stay native paths; `devcontainer.json` never changes a production run or implicitly selects a mode. An explicit native command and readiness probe keep normal precedence; otherwise use OCI argv, with existing empty-command refusal. No injected lifecycle script or keepalive. Validate the exact expanded user-data budget before allocating resources; unsupported lane/profile, invalid structured input or binding mismatch must not fall back. Guest-dependent path, identity or access failures must prevent dev readiness and leave owned state for normal reconciliation/deletion.

Existing workload `chroot` and `/connection` address metadata are not developer session entry. Add an owner-authenticated guest entry path in the qualified CPU dev boot profile: SSH key authentication with pinned guest host identity and owner-authorized console PTY access use a trusted broker outside the workload overlay. Require the exact instance and ready overlay (never infer from Nova `ACTIVE`), enter the verified workspace, drop to the effective session user, then start a non-login guest shell with session env; do not expose a carrier shell or trust image-provided connection parameters. Do not treat raw serial logs, OpenStack management SSH or provider console access alone as this proof. The guest access profile must confine untrusted workload/session code away from carrier files, block devices, control sockets, metadata-provider credentials and management services; use known runtime confinement including no new privileges, no supplementary groups, no setuid/capability escalation and bounded PTY sessions. A plain chroot is not this security boundary. Scope forwarding, if enabled, to the same authenticated SSH access and exact TCP endpoints; disable it otherwise. Expose only authorized, non-secret connection/profile summaries via the API; dashboard displays those and launch refusal without embedding a browser IDE or assuming a browser can bind client loopback. Do not report a port as active until the client actually opens it.

`Stop`/shelve closes current sessions/forwards; `Resume` revalidates and reuses the same ordered lowers, private writable data and effective profile, never re-parses Git or reinitializes the workspace. Re-import/rebuild targets a different immutable job and fresh VM, not a rewrite/rebase of existing data. Document explicit deletion of the instance's dedicated boot/upper storage under current ownership/cleanup checks; no data volume is attached, recaptured, or destroyed by conversion. Never pass provider secrets or bootstrap/session capabilities into guest user env. If downgraded code cannot enforce the binding or access policy, block affected build and launch/resume ingress before rollback; do not reinterpret managed records as ordinary or delete retained data.

## Owner decisions required before implementation

1. **Product / access:** Confirm the initial private Hub CPU dev lane, baked workspace without host sync, and managed SSH plus console access in the workload overlay. If actual-root (or local checkout support) is required for M5.2, require a qualified authoritative lane instead of labeling the current carrier path as native or substituting this for M4 evidence.
2. **Lifecycle trust:** Confirm all config hooks are rejected, including permanent no host initialization. If guest-only hooks are desired, approve a separate execution and replay policy before enabling any.
3. **Features trust:** Confirm no Features. Any later exception needs approved supply-chain pins, fetch and sandbox scope; no automatic Feature install or image-label merge.
4. **Port exposure:** Confirm default deny; decide whether to enable only owner-authorized client-loopback TCP forwarding through managed SSH. Public/provider ingress or browser relays are not covered.
5. **Selectable volumes / persistence:** Either approve an exact-owner selectable-volume contract within M52-02 (allowed selection and guest targets, ownership, attachment, retention, backup and cleanup evidence), or record an owner-approved roadmap amendment under a new ID with the original volume obligation traceable. Until that disposition and its applicable evidence are recorded, do not close M52-02 or GATE. The baked workspace and private writable upper do not satisfy the volume clause. Neither option authorizes arbitrary host binds, sockets or automatic attachments.
6. **Guest identity:** Confirm the non-root-only rule for both workload and developer sessions, including rejection of the current root OCI default when config supplies no valid non-root `containerUser`. Broader identity support requires a separate security policy and qualification.
7. **Labeled images:** Confirm post-build refusal of any final `devcontainer.metadata` label, including metadata inherited from a base. Any alternative requires a separate metadata trust and compatibility policy, not unchecked upstream merging.
8. **Dashboard qualification:** Decide whether Hub `/app` or deployed Afterglow dashboard evidence satisfies M52-03 and document the required user journey on that surface. Do not substitute Hub `/app` or API documentation for Afterglow's separate M4-15 requirement.

# CI critical-path and safety specification

This is the migrated `AGENTS.md` CI rules 1–12 for *Palimpsest*, not another repository's CI/approval state. [`development-handoff.md`](../../../docs/development-handoff.md#ci-critical-path-checkpoint-2026-09-24) retains the dated measurements, rollout, conflicts, and owner decisions. The numbers below are observations or estimates as labeled, not fresh verification. CI/workflow and repository settings are unchanged by this documentation migration.

## Baseline (2026-09-24 read-only measurement)

The 19-job `.github/workflows/test.yml` form entered dev at `1a23f9c`. Among 21 completed `Test` runs from September 15–23, critical path (creation, or `run_started_at` for reruns, to last job finish) median was 325 s, p90 781 s. Excluding eight September 21 12:39–12:43 runs serialized on the sole KVM runner, the other 13 had median 303 s, p90 346 s. `Unit tests (macOS 15)` finished last in 19/21 runs. `portable-macos` `max-parallel: 2` made a second wave (shards 3/4 and 4/4 median waits 151/170 s); `portable-linux` `max-parallel: 3` likewise (shards 4–6 waits 91–105 s). The single `pieroot-server-palimpsest-kvm` runner serialized `Native KVM stage-1 proof`: execution 140 s, median wait 142 s, p90 626 s. The September 24 `ci-perf` change removed both matrix caps; predicted 155–170 s dev/PR critical path (bounded below by ~140 s KVM) was an *estimate*, not verified improvement. The handoff records three later green posted runs (192/182/157 s), not the required 20-run before/after distribution.

## Requirements

### 1. Measure before optimizing

Before and after a CI change, collect job and step timings for at least 20 recent `Test` runs with `gh run list --workflow test.yml` and `gh api repos/openstack-afterglow/palimpsest/actions/runs/<id>/jobs`. Record critical-path median/p90 in the commit body, handoff, and `ARCHITECTURE.md` Maintenance summary. Do not sum individual savings or claim improvement without observed before/after CI; optimize the last-finishing job first. Do not manufacture samples by forced workflow runs to satisfy the threshold.

### 2. Optimize wall clock within shared concurrency limits

This public repository uses free GitHub-hosted time; wall clock is the goal. Organization Free limits of 20 hosted and five macOS concurrent jobs are shared with lumen, openstack-afterglow, drover, waygate, and afterglow-crypto; only this repository uses macOS. Workflow-definition counts (not observed utilization): one `Test` starts 15 hosted jobs including four macOS, then three aggregators, total 18; self-hosted KVM is excluded. The same push on `main`/`dev` also starts Hub `test` and development-package `verify` (17 hosted at start); a PR targeting `main`/`dev` adds Hub `test` (16). Simultaneous dev/main pushes (17+17, macOS 4+4) exceed org limits. Measure overlapping-run queueing, not only individual run time.

### 3. Preserve parallel checks and publication gates

`Lint, manifests, and package` (`checks`) must not become a portable-shard `needs:` gate. Only `Pure contracts (Python 3.12)`, `Unit tests (macOS 15)`, and `Required native KVM proof` aggregators have both `if: always()` and `needs:`; `checks` joins in the Pure contracts aggregator. Publishing/pushing images or packages and deploying should be gated on the entire `Test` result; a nonpublishing PR verification build may run in parallel (`hub-docker.yml` PR `build-and-push` builds two images with `push: false`). **Existing unresolved exceptions, not permission to change them:** `hub-docker.yml` push/tag/dispatch `build-and-push` pushes to GHCR after its own `Hub Unit Tests` only; `development-package.yml` `publish` creates an exact-SHA prerelease after only its `verify` (`core-cli`, `qualification`, development-package contract, architecture freshness, CLI reference, lane manifest, targeted Ruff, package build); `release.yml` PyPI `publish` then `github-release` depend on own `verify` and `kvm-proof` (unit, Kolla, guest stage-1, BuildKit; not macOS or all portable). They lie outside `Test` critical path; altering their publishing semantics needs the owner's decision in the handoff's CI checkpoint approval item 3. Do not quietly reclassify a publication as a harmless PR build.

### 4. Track fixed cost

Measure checkout, `setup-uv`, `setup-python`, and `uv sync --frozen --extra dev`. September 2026 Linux shard overhead was ~6 s, macOS ~9 s, ~7% of job duration each; `setup-uv` v6 default caching left sync ~1 s. If cache restore exceeds reinstall, do not cache. For added service containers use a short health-check interval (e.g. 2 s), sufficient retries/start-period.

### 5. Shard only when economical, launch one wave, preserve the known gap

Portable shards use `scripts/test_lanes.py` stable SHA-256 keys (module/class/function and parameter index). Workflow steps directly invoke `uv run python scripts/test_lanes.py run portable --shard ${{ matrix.shard }}/M`; no wrapper that may omit arguments or `-- --shard`. Matrix shard list, command denominator, and job-name denominator must agree; `max-parallel` absent or >= shard count. Each shard prints a "Lane shard" count, but CI *does not check* that count or the shard sum against the portable total. Runtime fail-closed paths: empty shard pytest exit 5, collection error exit 2, `--test-lane-shard` passed without plugin usage error exit 4. `test_ci_portable_matrix_runs_every_shard_in_one_wave` pins all shard steps and exact command to prevent a wrapper omitting `--shard` and running the full suite on each shard; in that omission the plugin receives no `--test-lane-shard`, so exit 4 does not protect it. `test_portable_command_shards_nodes_without_special_selectors_or_environment_mutation` checks `commands()` pytest argv; `test_node_shards_are_deterministic_disjoint_and_complete` and `test_separate_process_random_uuid_parameters_have_exact_complete_shard_union` check disjoint/complete assignment.

These contracts do **not** guard workflow-external disabling. For example `pyproject.toml` `addopts = "--collect-only"` or a conftest hook can prevent execution while each shard prints counts and exits 0. September 24 `PYTEST_ADDOPTS=--collect-only` with `run portable --shard 1/256` selected 24 nodes, ran zero, exited 0. The shared rule demanding a runtime executed-count check is **not met**. Owner must decide to implement selected-vs-executed checking or accept the deviation (handoff CI checkpoint item 4); do not present the wrapper contract as that runtime check. Reassess queueing and org caps when changing shard count.

### 6–7. Isolation, hermeticity, and xdist prerequisites

No global state sharing or process reuse optimization: first shuffle at least twice to check leaks, then explicitly opt in only safe files. Restore modified environment/global state via monkeypatch/fixtures and preserve session-pinned `PALIMPSEST_LOG_HOME` in `tests/conftest.py`. Portable tests must not rely on real KVM/libvirt/Docker/remote services/host-global directories; host configuration changing behavior or runtime is a defect. No pytest-xdist currently. Before adoption, prove hermeticity by shuffling (Linux 6/6 had an unresolved 0.1 s lock-timeout flake), restore "Lane shard" evidence because xdist controllers do not run `pytest_collection_modifyitems`, and set workers to runner vCPU explicitly; never use `-n auto`.

### 8. Correct diff ranges for any future change detection

There is currently no CI change detection; every push/PR runs full portable. `test_lanes.py plan --changed` is a local selector. If adding CI detection: push compares `github.event.before..github.sha`, with all tests on zero SHA, force push, or fetch failure. PR compares merge base with `git diff --name-only <base>...<head>`, or on `refs/pull/<n>/merge` compares the merge commit's `HEAD^1..HEAD`; run all if base fetch fails. Do not compare PR tip directly with `git diff <base>..<head>` (it includes base-only changes) or compare only last commit via `HEAD^1..HEAD` on push/PR-head checkout. The merge-ref *merge commit* is the sole `HEAD^1..HEAD` exception because its first parent is base tip. This deliberately specifies the shared rule's "base..head" as merge-base semantics, not Git two-tip syntax. Published Hub image/development package decisions must use the actual published revision.

### 9. Deduplicate only identical tested inputs

Skip a PR test only if it is a same-repository branch PR, its merge tree equals head tree, **and** a completed `Test` push of that head branch tested the same tree. Never use branch name alone (fork collision). `test.yml` pushes only `main`/`dev`, so other head branches, including `codex/oci-root-phase1`, have their sole `Test` run on PR and cannot skip. Fork and Dependabot PRs always test. September 2026: 7/14 current-form push runs were near-simultaneous same-SHA dev/main pushes (3–6 s apart) with KVM queue waits 142–144 s. Owner must decide whether to avoid that by workflow/merge practice (e.g. fast-forward main only after green dev).

### 10. Do not execute public pull_request code on the persistent self-hosted runner

In `Test`, only `kvm` uses `[self-hosted, linux, x64, kvm]`; `release.yml` `kvm-proof` also uses that runner only on `v*` tag push. Required control has **two layers**: YAML `github.event_name != 'pull_request'`-style event gate to keep PR execution off the runner, and repository/org settings as backstop because a PR run uses its PR-side workflow and can remove its YAML gate. Settings alone cannot distinguish same-repository PR, Dependabot PR, or approved fork PR: fork approval applies only to forks and approvals let execution proceed; runner-group repository restriction cannot separate triggers within a repository. Ref-specific workflow access may help if offered on this plan, but availability was not established.

**Unresolved as of 2026-09-24, not a safety claim:** `kvm` has only `if: vars.PALIMPSEST_KVM_ENABLED == 'true'`, so PR jobs reach the persistent runner; that variable test is in editable YAML. Fork policy is `first_time_contributors`. Runner `pieroot-server-palimpsest-kvm` is repository-level with no runner group; org plan `free`, runner-group API returned 403, extra groups documented for Team and above, default-group restrictions unconfirmed. `.github/dependabot.yml` absent; security-update setting unconfirmed. Previous readonly query listed 22 same-repository PR runs, no fork runs; KVM run `35600862976` (`dev`) and `35600812317`/`35029001178` (`codex/oci-root-phase1`) were same-repository PRs, **not observed fork-code execution**. Still, under `first_time_contributors`, an external fork author with a prior merged contribution may run without approval. Stopping/unregistering the runner is the known way to eliminate exposure including a PR modifying workflow before both layers can be established; it affects availability and needs owner authorization.

Setting changes are owner-only and need explicit approval: repository Settings → Actions → General → Approval for running fork pull request workflows from contributors → Require approval for all external contributors → Save; group restriction first requires re-registering this repository runner as org-level, then org Settings → Actions → Runner groups → Selected repositories (this repo), optionally ref-specific workflow restriction if available. Neither setting alone suffices. **Conflict:** adding YAML gate skips `kvm` on PR; `Required native KVM proof` then marks skip failure and turns all PRs red, while `test_ci_test_jobs_start_without_a_gate_job_in_front` exactly pins the present `kvm` `if`, and existing no-skip rule forbids treating a skipped KVM proof as success. Owner must decide what PR required proof means (e.g. PR-only conditional skip verdict or remove PR-required check), then change gate, aggregator verdict, contract, and this rule together; until then do not make a skipped proof green. Handoff approval item 1 and the explicit approval block item 2 are the same unresolved decision. `release.yml` `kvm-proof` has no job-level permissions, inheriting workflow `contents: write`/`id-token: write`; persistent state from an earlier PR could reach that later release token. This expands the potential impact beyond one read-token Test job; it is not proof of actual compromise.

### 11. Pin CI shape honestly, including contract blind spots

`tests/unit/test_test_lanes.py` pins portable Linux/macOS matrix jobs: exact job keys `name`, `runs-on`, `strategy`, `steps` (no job `if`/`env`/`defaults`/`continue-on-error`), runners `ubuntu-latest`/`macos-15`, strategy keys only `fail-fast`, `matrix`, `max-parallel` with `{shard: [1..N]}` (no include/exclude), `fail-fast: false`, no `max-parallel` below N, and the complete exact step list/action versions/`with`/command and denominator (no step `if`/`shell`/`env`, checkout `ref`, extra `$GITHUB_ENV` step); no workflow-level `env`.

The three aggregators have exact names, `if: always()`, `needs`, single verdict-step `env` per `needs.<dep>.result` (KVM also variable) and success-only exact `run`. Aggregator/verdict cannot set `shell`, `defaults`, `continue-on-error`; workflow cannot set `defaults`/`env`. All 11 `test.yml` job IDs and job-key sets are pinned; new jobs must enter that contract. No job-level `env`, `permissions`, `continue-on-error`; only aggregators and `kvm` may have `if`, only `hub` may have `defaults` exactly `{run: {working-directory: hub}}` (not `defaults.run.shell: "true {0}"`). Top level exactly `name`, `on`, `permissions`, `jobs`; permissions exactly `{contents: read}`, so no workflow concurrency/write token. All workflow steps forbid `shell` and `continue-on-error`; step `if` only `always()` (upload/cleanup, not bypass). `checks` must not gate test jobs and only `kvm` has nonaggregator job `if` pinned to `vars.PALIMPSEST_KVM_ENABLED == 'true'` pending owner decision.

Across workflows, allowed hosted runner labels are exactly `ubuntu-latest`, `ubuntu-24.04`, `macos-15`; all other jobs must be only `test.yml` `kvm` or tag-only `release.yml` `kvm-proof`. A self-hosted runner can use an arbitrary label, so inspect string/list/mapping `runs-on` (`group`, `labels`), and treat missing `runs-on` as nonhosted. New hosted images require explicit allowlist labels. No reusable-workflow `uses:` jobs (a caller of `test.yml` inherits self-hosted KVM). `test.yml` triggers exactly `workflow_call`, `main`/`dev` push, and `main`/`dev`-targeted `pull_request` (no `pull_request_target`); `release.yml` only `v*` tag push. No workflow may use `pull_request_target` or `workflow_run` (empty allowlist), including alternate string/list/mapping `on` forms: fork-triggered runs could access base token/secrets and PR code via head checkout/artifacts. `tests/unit/test_oci_convert_security.py` text-pins no job-level `if` between `oci-fs-proof` and `unit-macos`; do not reorder that section.

**Not pinned:** non-matrix `checks`, `hub`, proof-job step content (`env`, `$GITHUB_ENV` additions); `kvm` evidence absent still fails at upload `if-no-files-found: error`. No protection from workflow-external `pyproject.toml` addopts/conftest execution suppression (rule 5). For non-`test.yml` workflows, `test_test_lanes.py` checks triggers/runners/reusable calls only. `tests/unit/test_development_package_workflow.py` checks development-package trigger (`workflow_dispatch` plus three allowed branches), workflow `{contents: read}`, per-ref concurrency, IDs `verify`/`publish`; `verify` absence of job-level permissions, branch-ref comparisons in job `if`, and six required substrings in concatenated step `run` text. Those are *inclusion*, not actual execution checks: `|| true`, `echo`, or skipping a test step can pass; `qualification` and Ruff are not mandatory substrings. For `publish` it checks `needs: verify`, `{contents: write}`, exact `uses`, a `sha256sum --check SHA256SUMS` run preceding helper run (order only), helper `--repository`/`--sha`/`--dist-dir`, and forbidden strings (`gh api`, `gh release create`, `--clobber`, etc.). It text-checks release `v*` and PyPI `publish` dependencies/condition. It does **not** pin either development-package job's key set, step `if`/`shell`/`continue-on-error`/`env` or additional steps; `verify` job `if` only has inclusion checks. Skipping/ignoring verify failure can publish an unverified SHA-specific prerelease under write permissions. Inspect this gap manually when changing that workflow: nine September 24 temporary mutations (verify step `continue-on-error`, `if: false`, `shell: 'true {0}'`; verify job `continue-on-error`; checksum step `continue-on-error`, `if: false`; publish job `if: always()`; `echo` wrapping; verify `if` `|| true`) all passed the existing three CI-contract files. Extend existing CI-contract files for new invariants rather than creating new unclassified test files (`scripts/test_lanes.py` classifies tests).

### 12. Reassess continued performance and architecture freshness

Attach observed before/after timings for CI changes. Remeasure under rule 1 if `Test` critical-path median rises at least 20% from last recorded baseline, portable nodes grow substantially, or a new test tier/job is added. Baseline portable selected-node sum was 6,081 on `60fa42f` CI run `35826465548` (same across Linux six and macOS four; *not pass count*); later local snapshots were 6,084 at `2e37538`, 6,088 after review 1, 6,089 after review 2, 6,091 after review 3 (`--collect-only`). `.github/**` and `AGENTS.md` are architecture-digest inputs: a normal CI/root rule change requires an updated Maintenance summary, stamp, and staged check per architecture procedure. A specifically scoped documentation migration forbidding stamps/checks does not itself provide fresh guard evidence.

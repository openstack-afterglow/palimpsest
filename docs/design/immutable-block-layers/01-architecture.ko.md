# 산출물 1 — 통합 아키텍처와 데이터 흐름 명세

상태: 설계 제안입니다. 승인된 아키텍처가 아니며 제품 코드(클라이언트, Hub)는 바꾸지 않았습니다.

근거 표기: **[실행]** 일회용 Linux VM에서 이 저장소의 스크립트로 직접 확인, **[문서]** 상위 프로젝트 문서,
**[소스]** 상위 프로젝트 소스 판독(실행 아님), **[추론]** 그로부터의 추론, **[미검증]** 확인하지 못함.
실행 환경과 수치는 [README](README.ko.md)에 있습니다. MB는 10^6바이트, MiB·GiB는 2의 거듭제곱 단위입니다.

## 1. 요약

- 가상 디스크 하나를 **불변 블록 레이어의 순서 있는 목록**과 **쓰기 계층 하나**로 표현합니다. 레이어 0은
  부팅 가능한 Ubuntu 22.04 디스크 전체, 그 위 레이어는 각각 한 번의 변경(CUDA, cuDNN, PyTorch, 사용자
  작업)이 바꾼 블록입니다. 형식은 OverlayBD(LSMT + ZFile)입니다.
- 같은 레이어 블롭을 **OCI 레지스트리**(개발자 머신의 지연 로딩)와 **Ceph RBD 풀 `lib-layers`**(데이터센터,
  1본)에 올립니다. 블롭의 SHA-256이 두 곳에서 같은 식별자입니다.
- 데이터센터에서는 컴퓨트 노드가 `[레이어(RO, krbd) + 사용자 delta(RW, RBD)]`를 OverlayBD로 조립해 블록
  장치 하나로 만들고 그것을 VM의 루트 디스크로 붙입니다. 로컬에서는 같은 조립을 레지스트리에서 읽으면서
  합니다.
- 요청하신 구성에서 달라진 점(6절): `ceph-immutable-object-cache`는 이 구조(krbd로 매핑한 레이어)에
  적용되지 않습니다. `exclusive-lock`은 요청대로 레이어에는 없지만 다중 노드 읽기의 조건은 아니었고, delta에는
  오히려 필요합니다. 프런트엔드는 `ublk`가 아니라 TCMU입니다. "독립된" 증분 레이어는 부모 체인에 묶입니다(3절).
- OverlayBD의 쓰기 계층을 VM 디스크로 쓰려면 README 절차에 없는 **세 가지 호스트 설정이 필수**였습니다
  (4 KiB 쓰기 정렬, flush 전달, 타임아웃). 앞의 두 가지는 없으면 데이터가 손상되거나 flush한 쓰기가 호스트
  메모리에만 남는 것을 실행으로 확인했고, 타임아웃은 소스 판독에 근거합니다. 참조 구현은 셋 모두를
  강제합니다(6절, [산출물 3](03-provisioning.ko.md) 2절).
- 로컬 경로와 Ceph 저장·조립 경로, libvirt 훅은 실제로 실행했습니다. **Nova/Cinder를 통한 연결, 여러
  호스트, GPU, 성능은 실행하지 않았습니다.**

## 2. 용어

| 용어 | 뜻 |
| --- | --- |
| 레이어 블롭 | `overlaybd-commit -z`가 만든 ZFile 한 개. SHA-256으로 식별하며 불변 |
| 스택 | 가상 디스크 크기와, 아래에서 위 순서의 레이어 목록(digest, 크기, UUID, 부모 UUID). 불변이며 이름을 덮어쓸 수 없음 |
| 세션 / delta | 스택 위의 쓰기 계층 하나(sparse 파일 `data`, `index`). commit하면 새 레이어가 됨 |
| 게시 | 블롭을 레지스트리(`oras`)와 RBD(임시 이름으로 import → `@sealed` 스냅샷 보호 → 재검증 → 최종 이름)에 올림 |

## 3. 레이어 모델과 그 한계

```
가상 디스크(예: 20 GiB, GPT)
 ┌───────────────────────────────────────────────────────────┐
 │ 쓰기 계층 (세션/사용자 delta, sparse 파일)       RW  4 KiB 단위      │
 ├───────────────────────────────────────────────────────────┤
 │ L3  PyTorch가 바꾼 블록                          RO                │
 │ L2  cuDNN이 바꾼 블록                            RO                │
 │ L1  CUDA 툴킷이 바꾼 블록                        RO                │
 │ L0  Ubuntu 22.04 디스크 전체(파티션 테이블·ESP·루트 ext4)  RO       │
 └───────────────────────────────────────────────────────────┘
   읽기: 그 블록을 가진 가장 위 레이어.  쓰기: 항상 쓰기 계층.
```

- **레이어 0은 디스크 전체입니다.** `overlaybd-apply --from_qcow2 --no-extract-rootfs`로 클라우드 이미지를
  그대로 블록 레이어로 바꾸고, 가상 크기까지 파티션과 파일시스템을 한 번 늘리며 inode 테이블 초기화까지
  끝내 둡니다(그렇지 않으면 모든 인스턴스가 첫 부팅 때 같은 변경을 자기 delta에 씁니다). 펌웨어가 그대로
  부팅하므로 커널을 따로 넘길 필요가 없습니다. [실행: aarch64 UEFI. amd64는 미실행]
- **레이어는 블록 변경이지 파일 변경이 아닙니다.** 그래서:
  - **특정 부모 체인에만 유효합니다.** CUDA 레이어는 그것을 만든 base 위에서만 의미가 있고 다른 base에
    얹을 수 없습니다. 레이어는 저장·전송 단위로는 독립적이지만 **재조합 단위로는 독립적이지 않습니다.**
    base를 바꾸면 그 위 레이어를 모두 다시 만들어야 합니다. 각 레이어는 부모의 UUID를 기록하지만 OverlayBD는
    장치를 열 때 그 순서를 강제하지 않습니다. [소스] 순서를 지키는 것은 스택 설명(digest 목록과 부모 UUID
    사슬 검사)입니다.
  - **지운 파일의 블록이 남습니다.** `fstrim`으로 버려야 빠집니다. 300 MiB 파일을 쓰고 지운 세션의 쓰기
    계층은 trim 전 301 MiB, trim 후 340 KiB였습니다. [실행: 수동, `dm-ebs` 경유] discard된 블록은 장치를 다시 열면 0이 아니라
    하위 레이어의 내용으로 읽힙니다. [실행]
  - **ext4 저널이 레이어에 섞입니다.** 메타데이터 변경은 저널을 거치고 저널 블록은 해제되지 않습니다. 저널
    없이 빌드한 뒤 빈 저널을 되돌리면 훨씬 작아집니다([산출물 2](02-build-and-publish.ko.md)의 표). [실행]
  - **쓰기 단위는 4 KiB입니다.** LSMT 색인 자체는 512바이트 섹터 단위이지만 [소스], 이 설계가 쓰는 sparse
    쓰기 계층은 기록 여부를 데이터 파일의 hole로 복원하므로 실제 단위는 그 파일시스템의 블록(4 KiB)입니다.
    요청하신 "4KB 블록 단위"와 같습니다. 다만 이것은 보장이 아니라 **지켜야 하는 조건**이었습니다: 4 KiB보다
    작은 쓰기가 그대로 내려가면 다시 열었을 때 같은 블록의 나머지가 0이 됩니다. [실행] 그래서 `dm-ebs`로
    4 KiB 정렬을 강제합니다.
- **쓰기 계층은 하나이고 항상 맨 위입니다.** 하위 레이어는 최대 255개입니다. [소스]
- **가상 크기는 스택에서 고정됩니다.** 크기를 바꾸는 도구(`overlaybd-resize`)는 있으나 다루지 않았습니다.
- **파일 의미는 게스트 파일시스템의 것입니다.** whiteout·opaque 같은 OCI 레이어 의미는 없고, 현재
  Palimpsest의 SquashFS 레이어와 섞어 쓸 수 없습니다(11절).

## 4. 구성요소와 데이터 흐름

```

 jammy 클라우드  │ build-base : overlaybd-apply --from_qcow2 → 크기 확장      │
 이미지(qcow2) ─▶│ build-layer: 조립 → chroot 레시피 → fstrim → 저널 초기화    │
                │ commit     : overlaybd-commit -z  → 블롭(sha256)            │
                └───────────────┬───────────────────────────┬──────────────┘
                     push(oras) │                           │ rbd-publish
                                ▼                           ▼
                   ┌─ OCI 레지스트리 ─┐          ┌─ Ceph RBD: lib-layers ──────┐
                   │ 매니페스트        │          │ blk-<sha256>@sealed (1본)   │
                   │ 블롭(HTTP Range)  │          │ 기록: publisher 자격만       │
                   └───┬──────────▲───┘          └──────────────┬─────────────┘
          pull(매니페스트)│          │ push(새 블롭 1개)            │ krbd map --read-only
                        ▼          │                            ▼   (노드당 1회, 인스턴스 공유)
 ┌──── 개발자 머신 (Linux · Lima · WSL2) ────┐   ┌──────────── 컴퓨트 노드 ─────────────┐
 │ overlaybd-tcmu                            │   │ /dev/rbdA … /dev/rbdN   하위 레이어   │
 │   하위: 레지스트리 범위 읽기 + 로컬 캐시   │   │ <delta 풀>/volume-<id> ─ krbd --exclusive│
 │   상위: local-delta (sparse 파일)         │   │    └ ext4 └ {data,index} 상위(sparse) │
 │ /dev/sdX → dm-ebs → /dev/mapper/blk-…     │   │ overlaybd-tcmu → /dev/sdX → dm-ebs    │
 │   ─▶ QEMU/KVM virtio-blk (vda)            │   │   = /dev/blkstack/<volume-id>         │
 │ 종료 후 commit → 새 블롭                  │   │ libvirt prepare 훅 ◀ Nova(Cinder local)│
 └───────────────────────────────────────────┘   │ QEMU virtio-blk (vda)                  │
        동기화 작업: pull --blobs(검증) ─────────▶│                                        │
                    → rbd-publish(새 이미지 1개)  └────────────────────────────────────────┘
```

### 블록 장치 매핑과 I/O 경로

| 구간 | 데이터센터 | 로컬 |
| --- | --- | --- |
| 게스트 | virtio-blk `/dev/vda` | 같음 |
| 하이퍼바이저 | QEMU raw 블록 장치, `cache=none` → `/dev/blkstack/<id>` | QEMU → `/dev/mapper/blk-<hash>` |
| 정렬 계층 | `dm-ebs`: 512바이트 섹터를 4 KiB 블록 쓰기로 | 같음 |
| 커널 | SCSI 디스크 `/dev/sdX`(write-back 표시, 타임아웃 상향) → tcm_loop → TCMU 링 버퍼 | 같음 |
| 사용자 공간 | `overlaybd-tcmu`: 열 때 만든 병합 색인으로 블록 위치를 찾고 ZFile 압축을 풂 | 같음 |
| 읽기(하위) | krbd 블록 장치(스냅샷, RO) → OSD. 캐시는 호스트 페이지 캐시(`ioEngine` 0일 때) | 레지스트리 HTTP Range → 파일 캐시(`cacheDir`) |
| 쓰기(상위) | sparse 파일 → ext4 → krbd(RW, exclusive) → OSD. flush는 `fdatasync`로 내려감 | sparse 파일 → 로컬 디스크 |

결합 원리는 한 가지입니다. OverlayBD는 "하위 레이어 파일들 + 상위 파일 한 쌍"만 알면 되고, 그 파일이
레지스트리 블롭이든 RBD 블록 장치든 로컬 파일이든 같은 가상 디스크를 만듭니다. 같은 스택을 (가) 검증해
받은 로컬 블롭 파일, (나) RBD 읽기 전용 스냅샷 매핑, (다) 캐시를 비운 뒤 레지스트리 지연 읽기로 각각 조립해
20 GiB 전체를 읽은 SHA-256이 일치했습니다. [실행]

## 5. 데이터센터 연동

- **저장 중복 제거**: 레이어는 `lib-layers`에 이미지 1개씩만 있습니다. 한 노드에서 두 인스턴스의 디스크를
  동시에 조립했을 때 레이어 매핑은 3개 그대로였고, 한 인스턴스를 해제해도 다른 인스턴스의 매핑은
  유지되었습니다. [실행: 조립과 읽기까지. 두 VM의 동시 부팅은 하지 않음] 레이어보다 작은 단위(같은 파일이
  두 레이어에 있는 경우)의 중복 제거는 없습니다.
- **Nova/Cinder**: Nova는 수정하지 않습니다. Cinder 백엔드가 기존 연결 유형 `local`과
  `/dev/blkstack/<volume-id>` 경로를 돌려주면 Nova 2026.1은 그것을 `<disk type='block'>`으로 씁니다. [소스]
  장치는 libvirt `prepare` 훅이 QEMU 시작 전에 노드 에이전트를 통해 만듭니다. 훅과 에이전트는 Nova 없이
  `virsh`로 실행해 확인했습니다. [실행] Cinder 드라이버는 스케치이며 실행하지 않았습니다. [미검증]
  자세한 내용은 [산출물 3](03-provisioning.ko.md).
- **과금**: delta 이미지의 `rbd du`로 측정합니다. 정의와 한계는 8절과 산출물 3.

## 6. 요구사항과 달라진 점, 추가로 필요했던 것

| 요구사항 | 확인한 사실 | 이 설계의 선택 |
| --- | --- | --- |
| 다중 노드 동시 마운트를 위해 `exclusive-lock` 비활성화 | 읽기 전용 krbd 매핑은 exclusive lock과 watch를 잡지 않고, 스냅샷 매핑은 항상 읽기 전용입니다. [소스: Linux 6.8 `rbd.c`] | 요청대로 레이어 이미지에는 이 기능이 없습니다(`layering`만). 다만 그것이 조건은 아닙니다: 레이어는 보호된 스냅샷으로 매핑합니다. delta에는 반대로 `exclusive-lock`을 켜고 `--exclusive`로 매핑해 이중 쓰기를 막습니다 |
| `ceph-immutable-object-cache`(로컬 NVMe) | librbd가 clone의 **부모**를 읽을 때 동작합니다. [문서·소스: `ParentCache.cc`] krbd 매핑에는 적용되지 않습니다 | 이 구조(krbd + OverlayBD)의 레이어 읽기 캐시는 호스트 페이지 캐시입니다. NVMe 캐시가 요구사항이면 librbd 경로가 필요합니다: 10절의 대안 B, 또는 산출물 3의 대안들 |
| `ublk` 또는 `tcmu` | 최신 릴리스 v1.0.18 패키지에는 `overlaybd-tcmu`만 있습니다. [실행: 패키지 목록] ublk 프런트엔드는 미출시 main에 있고, 그 문서는 5.10 백포트 커널에서 검증했고 mainline 6.x 회귀는 대기 중이라고 적습니다. [문서] | TCMU. ublk는 릴리스에 포함되고 대상 커널에서 검증된 뒤 다시 평가합니다(8절) |
| 쓰기 계층은 4KB 블록 단위 CoW | sparse 쓰기 계층의 단위는 4 KiB가 맞지만 강제되지 않습니다. 512바이트 쓰기가 내려가면 다시 연 뒤 손상됩니다. [실행] | `dm-ebs`로 4 KiB 정렬을 강제합니다 |
| `rbd du` 기준 과금 | 기본값은 object(4 MiB) 단위 올림이고 `--exact`가 구간을 셉니다(느림). [소스] 측정 대상은 delta 이미지 안 ext4의 RBD 구간입니다 | `--exact`를 기준값, 기본값을 빠른 근삿값으로 둡니다(8절) |
| User Delta RBD를 쓰기 계층으로 | OverlayBD의 쓰기 계층은 파일 두 개이고 sparse 방식은 파일 hole에 의존합니다. [소스] 블록 장치를 직접 주는 것은 시도하지 않았습니다 [추론] | delta RBD 위에 ext4를 두고 그 안에 상위 파일을 둡니다 |
| 레이어를 RBD 이미지로 저장 | 블록 장치는 블롭 끝의 512바이트 미만을 잘라 보여 줍니다. `-z`로 commit한 ZFile은 색인 위치를 헤더에서 읽으므로 그 상태로 열리고 내용이 일치했습니다. [소스·실행] | RBD에 올리는 레이어는 `-z` ZFile로 고정합니다 |
| 로컬에서 "다운로드 없이" 스트리밍 | 지연 읽기는 CRC만 거칩니다. 블롭 전체의 SHA-256은 배경 내려받기가 끝난 뒤에만 확인되고, 그것을 끄면 한 번도 확인되지 않습니다. [소스] | 로컬 개발에서는 허용하되 명시합니다. 검증이 필요한 실행과 데이터센터 게시는 전체를 받아 digest를 확인합니다(7절) |

요구사항에 없었지만 필요했던 것 [모두 실행으로 확인]:

| 문제 | 관찰 | 조치 |
| --- | --- | --- |
| flush가 전달되지 않음 | `overlaybd-tcmu` 장치는 "write through"로 보여 커널이 flush를 보내지 않는데, 상위 파일 쓰기는 호스트 페이지 캐시에 머뭅니다. 64 MiB를 쓰고 `fsync`해도 delta 이미지에 반영되지 않고 호스트에 67 MB(65,668 kB)가 dirty로 남았습니다 | SCSI 디스크를 write-back으로 표시. 같은 시험에서 `fsync` 직후 반영 |
| 4 KiB 미만 쓰기의 손상 | 위 표 | `dm-ebs` |
| 30초 타임아웃 | 기본값이면 저장소가 30초 넘게 멈출 때 게스트가 I/O 오류를 받습니다 [소스] | 타임아웃 상향(설정값만 확인, 정지 상황은 미시험) |
| base의 inode 테이블 지연 초기화 | 레이어 빌드마다 수 MB씩 0이 섞이고 크기가 실행마다 달라짐 | base 빌드에서 한 번 끝냄 |

## 7. 무결성과 신뢰 경계

| 경로 | 무엇이 내용을 보증하는가 | 남는 위험 |
| --- | --- | --- |
| 빌드 → 블롭 | commit 직후 SHA-256을 계산해 그 이름으로 저장 | 빌드 호스트를 신뢰합니다. 레시피는 root로 실행되므로 일회용 빌더를 씁니다 |
| 블롭 → RBD | 임시 이름으로 올려 봉인한 스냅샷을 **클러스터에서 다시 읽어** SHA-256을 비교한 뒤에만 최종 이름을 줌 [실행] | 이후는 Ceph와 그 관리자를 신뢰합니다. 노드 자격은 레이어 풀의 이미지·스냅샷·메타데이터를 바꿀 수 없습니다 [실행: 다섯 가지 시도 거부] |
| 레지스트리 → 로컬(지연) | TLS와 레지스트리, ZFile의 CRC32C | **암호학적 검증 없이 블록이 게스트로 갑니다.** CRC는 변조 방어가 아닙니다. 캐시는 레지스트리 구분 없이 digest 이름으로 저장되므로 [소스] 한 레지스트리에서 받은 조각이 다른 레지스트리의 같은 digest에도 쓰입니다 |
| 레지스트리 → 데이터센터 | 동기화 작업이 `pull --blobs`(크기와 SHA-256 확인) 후 게시 [실행] | 매니페스트 서명은 다루지 않았습니다. digest는 "올라온 그 블롭"임을 보증할 뿐입니다 |
| 스택 설명(레지스트리, RBD 메타데이터, Glance 속성) | 경로·이름·인자로 쓰기 전에 형식 검사(digest, UUID, 크기, 레이어 수, 부모 사슬) | 형식이 맞는 임의의 조합은 막지 못합니다. 누가 설명을 쓸 수 있는지가 통제 수단입니다 |
| 사용자 delta | 자신이 기록한 스택 위에서만 조립됨. 이름으로 다른 스택을 지정하면 거부 [실행] | delta 내용 자체는 사용자 데이터이며 검증 대상이 아닙니다 |

경계가 달라지는 지점:

- **컴퓨트 호스트의 root 데몬이 레이어 형식을 해석합니다.** 사용자가 올린 블롭을 호스트의 `overlaybd-tcmu`가
  그대로 읽게 하면 파서 결함이 곧 하이퍼바이저 침해가 됩니다. 그래서 `lib-layers`에는 플랫폼 게시 작업만
  쓰게 합니다. 산출물 4의 "개발자 delta를 클라우드로" 흐름은 **플랫폼이 신뢰하는 게시자**를 전제로 하며,
  임의 사용자의 delta를 공용 레이어로 승격하려면 플랫폼 측 재빌드나 격리된 변환기가 필요합니다. 그 절차는
  이 제안에 없습니다.
- **호스트는 delta 이미지 안의 ext4를 마운트합니다.** 그 파일시스템은 호스트가 만들지만, delta 풀은 모든 노드
  자격과 Cinder가 쓸 수 있습니다. 마운트는 `nodev,nosuid,noexec,nosymfollow`로 하고 상위 파일이 일반
  파일인지 확인합니다. Cinder 백업 복원처럼 사용자가 고른 바이트를 delta 이미지에 쓰는 기능은 이 볼륨
  유형에서 꺼야 합니다.
- **호스트는 게스트의 파일시스템을 마운트하지 않습니다**(노드 경로). 게스트 디스크를 호스트에 마운트하는
  `blkstack trim`과 `build-layer`는 빌더와 자기 머신에서만 씁니다. 호스트의 udev·LVM이 게스트 디스크를
  스캔하지 않게 하는 설정이 필요합니다(산출물 3).
- **비밀값은 레이어에 남습니다.** 위 레이어에서 파일을 지워도 아래 레이어의 블록은 그대로입니다. 부팅한
  세션에는 호스트 키·machine-id 같은 첫 부팅 상태가 들어 있습니다.

| 항목 | 관찰 또는 사실 | 설계상 의미 |
| --- | --- | --- |
| 지연 로딩이 실제로 읽는 양 | 첫 부팅과 cloud-init 완료까지 레이어의 약 4분의 1(작은 스택), CUDA 스택(7.9 GB)에서는 3%가 캐시에 내려옴 [실행] | 네트워크가 느릴수록 이득이 큽니다. 반대로 레지스트리가 느리면 첫 부팅의 모든 블록 읽기가 그 지연을 받습니다 |

| 압축 | lz4 944 MB(2.3초), zstd 754 MB(5.7초) — base 레이어를 각각 따로 commit한 수동 측정 [실행] | 전송량과 CPU의 교환. 기본은 lz4, 대역폭이 좁으면 zstd |

## 9. 장애와 수명주기

| 상황 | 동작 | 근거 |

| delta의 파일시스템이 가득 참 | 게스트에는 쓰기 오류로 보입니다. delta 이미지를 가상 크기보다 크게 만들어 전체 덮어쓰기에도 자리가 있게 합니다 | 크기 규칙은 구현, 가득 찬 상황은 [미검증] |

## 10. 대안 B — 데이터센터는 RBD clone 체인, OverlayBD는 로컬과 교환 형식

요청하신 요구사항(1본 저장, 로컬 NVMe 캐시, delta 기준 과금, Nova/Cinder 연동)은 Ceph 자체 기능으로도
만족할 수 있습니다. 이 대안은 이 저장소에서 실행해 보지 않았습니다. 배경은
[OpenStack 공유 읽기 전용 레이어 검토](../../research/openstack-shared-readonly-layers.md)에 있습니다.

```
lib-layers/base@v1 ◀─clone─ cuda@v1 ◀─clone─ torch@v1 ◀─clone─ volumes/volume-<id> (사용자 delta)
      QEMU ── librbd ──▶ 사용자 clone 열기, 없는 object는 부모에서 읽음(ceph-immutable-object-cache 적용)
```

| | A: 호스트에서 OverlayBD 조립 (이 문서) | B: RBD clone 체인 |
| --- | --- | --- |
| 컴퓨트 노드 변경 | 호스트 데몬, `dm-ebs`, 에이전트, libvirt 훅, Cinder 드라이버 | 캐시를 쓰려면 노드마다 `ceph-immutable-object-cache` 데몬·전용 cephx 사용자·캐시 디렉터리와 librbd 설정(`rbd_parent_cache_enabled`, `rbd_plugins = parent_cache`). 캐시 없이라면 변경 없음 |
| 게시 | 블롭을 그대로 import | Cinder는 Glance 이미지에서 한 단계만 clone합니다. base → cuda → torch 체인은 직접 만드는 게시 작업과 Glance 위치 등록이 필요합니다 |
| 로컬 NVMe 캐시 | 해당 없음(페이지 캐시) | `ceph-immutable-object-cache`가 이 용도. 20.2.0에서는 데몬 시작 때 캐시를 비웁니다 [소스] |
| 라이브 마이그레이션 | 불가(정지 후 이동) | 기존 RBD 볼륨과 같음 |
| delta 단위 | 4 KiB 쓰기, 그 아래 ext4와 RBD object | RBD object(기본 4 MiB, 첫 쓰기 때 부모에서 복사) |
| 과금 | delta 이미지 `rbd du` | 사용자 clone `rbd du`. 부모에서 복사해 온 object는 자식 사용량에 들어갑니다 |
| 로컬과 같은 형식 | 예(같은 블롭) | 아니오. 레이어마다 OverlayBD 블롭 ↔ RBD diff 변환과 동등성 검증이 필요 |
| 개발자 delta를 클라우드로 | 블롭을 그대로 게시 | delta를 부모 clone에 적용해 새 스냅샷을 만드는 가져오기 작업 필요 |
| 하이퍼바이저의 사용자 데이터 해석 | 있음(7절) | 없음 |
| krbd 사용 시 체인 깊이 | 해당 없음 | 커널 6.8은 부모 체인 16단계까지 [소스] (librbd는 별도) |
| 이 문서에서 드러난 정합성 조건 | 정렬·flush·타임아웃을 호스트가 보장해야 함 | Ceph가 이미 처리 |

B는 운영 위험이 작고 요구사항의 캐시 조건에 맞습니다. A는 로컬과 데이터센터가 같은 블롭을 쓰고 delta를
변환 없이 올립니다. 어느 쪽으로 갈지는 12절의 결정 사항입니다.

## 11. 현재 Palimpsest와의 관계

- 현재 레이어는 **파일 수준**(SquashFS, 게스트 overlayfs, OCI whiteout 의미)이고 이 설계는 **블록 수준**입니다.
  둘은 섞이지 않습니다. 기존 레이어를 블록 스택에 쓰려면 변환(레이어마다 블록 레이어 생성)이 필요하고,
  변환 결과는 체인에 묶입니다.
- "부모는 불변 입력이고 새 부모는 새 계보"라는 원칙은 그대로이며 블록에서는 더 엄격합니다. 영향 범위를
  보여 주는 `palimpsest layer impact`의 사고방식이 그대로 필요합니다(부모가 바뀌면 위 레이어 전부 재빌드,
  기존 delta는 옛 스택에 남음, 자동 이전 없음).
- 호환성 단계 구분도 그대로입니다. 스택이 조립되고 부팅된다는 것은 구조 단계이고, ABI·커널·드라이버·
  애플리케이션 동작은 별도로 확인해야 합니다. 특히 GPU 드라이버는 레이어에 넣지 않습니다.
- 2026-10-29에 정한 저장 목표(Manila CephFS의 읽기 전용 레이어)와는 다른 방향입니다. 이 설계를 채택하면
  그 목표를 대체하거나 병행하는 결정이 필요합니다.

## 12. 결정이 필요한 사항

1. 데이터센터 방식: A(호스트 OverlayBD) / B(RBD clone 체인) / 실험 후 결정. A는 컴퓨트 노드의 신뢰 경계를
   바꾸는 변경이고, 이번에 드러난 정합성 조건(정렬·flush)을 호스트 운영이 계속 보장해야 합니다.
2. 파일 레이어(현행)와 블록 레이어의 관계: 대체, 병행, 변환 경로.
3. 지연 로딩의 검증 수준: 로컬 개발에서 "검증 없는 읽기"를 허용할지, dm-verity 같은 블록 단위 검증을 형식에
   넣을지.
4. 격리된 시험 환경: 여러 호스트, Nova/Cinder, 장애 주입(호스트 전원, 부하 중 데몬 중단, 저장소 정지), GPU,
   성능 측정은 운영 클라우드가 아닌 곳에서 해야 합니다.
5. 사용자 delta를 공용 레이어로 승격하는 절차와 권한.
6. 상위 프로젝트에 알릴 사항: 4 KiB 미만 쓰기의 손상과 flush 미전달은 OverlayBD를 컨테이너가 아닌 일반 블록
   장치로 쓸 때의 문제로 보이며, 상위 이슈로 보고할지 정해야 합니다(보고하지 않았습니다).
